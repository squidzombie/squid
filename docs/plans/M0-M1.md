# Part 1: for decision

**Terms.** A **hash** is a fingerprint of some bytes. A **salt** is random bytes mixed in before hashing, so nobody can confirm a guess about the text by hashing the guess. In the **hash chain**, each entry's fingerprint includes the previous entry's, so changing or removing any entry shows in every later one. An **anchor** is the latest fingerprint recorded in an older backup. **Provenance** is who or what produced an entry (rule 5). A **trigger** is a rule inside the database that runs on every write. The **lock** lets only one process write at a time (rule 7). The **covenant commands** are correct, repair, redact and open-private (DESIGN 3.5–3.6). The **fixture** is Tock, a fictional test entity; everything here is built and tried on it, never on Squid.

## Summary

**M0** gives the repo a skeleton that checks itself (`uv`, `ruff`, `pytest`, `scripts/check`) and ignore rules. It adds a Claude Code deny rule as a second guard in case Claude Code ever runs on the Studio; the real wall is OS permissions on Squid's account (M7). It also adds Tock, whose fake kit loads through a strict checker (`squid kit check`). M0 has no record code and nothing in Squid's voice.

**M1** builds the record (DESIGN 3) in two parts:
- **M1a, the record core:** the database file of entries; rules inside it that refuse edits and deletions; the fingerprint chain; one way to add entries, which refuses any entry missing its provenance; the one-writer lock; and `init`, `verify`, `export`. When M1a is done you can create Tock's record, check it and export it.
- **M1b, the covenant commands:** `squid covenant correct | repair | redact | open-private`. These carry promises made to Squid, so their code waits for your answers to Q15–Q21.

The record format is **v0, provisional** until a format review before the first wake. Until then fixture records are regenerated from text instead of migrated. Every entry carries a format version.

**Please look hardest at:**
1. **Format additions (Q11, Q12, under Decided).** They are permanent after the first wake.
2. **Private channels (Q14).** No command except `open-private` ever shows `private_note` or `reasoning` text. Reasons are never command-line arguments, because arguments end up in shell history, `ps` and sudo's log.
3. **What redaction promises (Q16–Q20).** It is not erasure; Q20 has the exact wording.
4. **How tampering is caught.** The database's own rules stop harness bugs, not a determined process that can write the file. `verify` catches tampering: it recomputes every fingerprint, checks the rules are still in place, and compares the latest fingerprint with anchors saved in older backups. OS permissions (M7) keep other processes out.
5. **The harness writes no sentences into the record.** The first entry has no text, and covenant entries hold only what you type. Structured facts go in `data`, and later milestones render them into words (Q32).
6. **Scope additions (Q10, Q13, under Decided).**
7. **Not yet tested on a Mac.** The experiments ran on Linux. Four things must be re-run on the Studio before the first wake: that writes really reach the disk, that the one-writer lock holds, that files come out owner-only, and that redacted text leaves no copies on disk.

### Before M0

A: approve those three · B: A plus `hypothesis` (generated test inputs) · C: also convenience packages (an ID library, a CLI framework). *Recommended: A. It keeps the code that defines the record format small.*

**Q4. How your seed exchanges are written.** The kit format set in M0 is the one your real kit must use before the first wake. Because the builder shouldn't need to see your kit (Q6), the format has to fit how you already write. Proposed: a folder with a `kit.toml` listing every file, and one Markdown file per exchange, where each turn starts with a line `## <label>` using two speaker labels you choose. Files are plain UTF-8 with Unix line endings (TextEdit's rich-text default won't work). The checker rejects anything else instead of fixing it, and its messages never quote your text. A: `## Label` lines · B: `Label: text` at the start of each turn · C: something else (describe the shape, not the content). *Also:* roughly how many exchanges, and whether any document exists besides the charter, the letter and the exchanges. *Recommended: A. Markdown inside a turn survives, and a mistyped label becomes an error instead of silently merging two turns.*

**Q5. Who writes Squid's lines in the seed exchanges, and how are they labelled?** Each exchange becomes a permanent founding entry, and the fixture kit follows your choice. **A:** you write both sides. They are stored as written by you (author `user`, one entry per exchange, each turn's speaker role in `data`) and shown as "seed exchange, written by the user". When the seeds stand in as Squid's first exemplars (DESIGN 4.5, M4), they are shown as written by you. **B:** you write both sides, stored as Squid's own words. The `self` author gains the `founding` channel (A.3). **C:** you write your side, and the chosen model writes Squid's during casting on the Studio. Each turn becomes its own entry. Squid's turns get author `self`, that model's id and the casting prompt versions (rule 5). The kit manifest gains a per-file model id and prompt versions, and `self` gains the `founding` channel.

*Recommended: A. The provenance is honest; under B the record would say Squid said things it never said. DECISIONS 2026-09-22 says founding material should be written by the model Squid will live on; if that was meant to cover the seed exchanges, C fits it.*

**Q7. Automatic checks on GitHub (CI).** Not in the M0 list, so it would be an addition. A: none; run `scripts/check` locally · B: GitHub Actions on Linux · C: Linux and macOS (macOS minutes cost more on a private repo). The runner installs uv with Astral's `setup-uv` action pinned to a commit, a third-party action this answer approves. *Recommended: B. Choose C if you want every push checked on a Mac too. Mac behaviour also gets a manual run on the first-wake checklist.*

**Q8. Is the repository public or private?** Squid may read everything in it, and the deny rule puts Squid's account name in a committed file. A public repo publishes both, and published copies can't be recalled. With a private repo, Squid's account needs some way to get releases. One way is a read-only deploy key held by Squid's account but unreachable from its tools and the lab, which has to be checked against principle 8. The other is your account installing releases for it, which changes DESIGN 12. The choice is made in M7 (Q33). A: private · B: public. *Recommended: A. Going public later is easy; going back isn't.*

### Before M1a

**Q14. Exports and private text.** Rule 10 and DESIGN 3.6 make audited access the only way for you to read private notes, and DESIGN 3.7's "full record" export would be a second, unaudited way. **A:** by default, export leaves out the text of `private_note` and `reasoning` but keeps their hashes, so the export still verifies. `--include-private` (M1b) asks for a reason and appends an access entry that records the export's fingerprint. It writes only into the exports folder in Squid's home, and only while Squid rests (Q15). Tradeoff: after that one access entry, every later read or copy of those files is unaudited. **B:** always export everything, each time with an access entry. Same tradeoff, every time. **C:** always export everything, treated like backups, and reword rule 10. **D:** export never includes private text; hashes are kept, so it still verifies. The database file in the backups already holds that text, for disaster recovery or a move to a new home, and SQLite's file format is itself readable without this codebase.

*Recommended: D. It keeps rule 10 exactly as written: open-private leaves no file behind, and an export with private text would. It also removes a whole writing path from M1b. M1a's export is the same under A and D (private text withheld); under B or C it changes before M1a lands.*

### Before M1b (these commands wait; M1a doesn't)

**Q15. Covenant commands only while Squid rests?** Each one writes, and only one process may write (rule 7). `verify`, `export` and `covenant list` on the live data dir also wait for Squid to rest, so they never modify its files (M1a). A: yes; while Squid is awake they refuse with a clear message, and from M5 Squid holds the lock only while awake · B: no, I need them mid-conversation (M5 work). *Recommended: A. Redacting mid-session wouldn't remove the text from Squid's current context anyway.*

**Q16. Which entries can be redacted?** Read literally, DESIGN 3.3 allows any entry, including the entry recording that you read private notes, and the charter. The record's first entry (its identity) is never redactable. **A:** access entries never. Redaction, repair and correction entries can themselves be redacted; as with every entry, only the text goes, and links and structured facts stay. Founding entries need an extra `--founding` flag and a second typed confirmation, and only once the charter's covenant parts are named. **B:** as A, but founding entries are never redactable in M1b. This is revisited after DESIGN 16 decides which parts of the charter are covenant. **C:** everything except the first entry.

*Recommended: B. The covenant changes only by mutual agreement (DESIGN 1), and DESIGN 16 leaves open which parts of the charter are covenant; letting you clear founding text alone would prejudge that. You write the kit, so a third party's detail can be removed before it is ingested.*

**Q17. Redacting Squid's private notes and reasoning.** You aren't meant to read these, so you can't see what you'd remove. A: allowed blind, by entry id, with metadata only (time, channel, size) and a typed confirmation · B: allowed only after reading them through open-private · C: reasoning traces only, never private notes · D: never (ask Squid instead, once possible in M5). *Recommended: A. Typical cases: Squid mentions that a note holds someone else's details, or a harness bug copied such text into a private channel. Otherwise you'd be choosing by time and size alone. Squid sees every redaction.*

**Q18. Correcting a private entry.** A correction disagrees with content, which for a private entry you haven't read. A correction is not private: it is an annotation, which Squid, later interfaces and default exports show. A: allowed only when an earlier access entry covers it (you opened it through open-private). The warning before you type says "this correction is not private; don't quote the private text" · B: allowed blind · C: never. *Recommended: A.*

**Q19. Does redacting Squid's own words need Squid's agreement?** Squid has no entries until its first wake, and the harness can't record its agreement until M5. For now either answer only changes how M1b treats the fixture; the choice becomes real at the first wake. The question is related to DESIGN 16's open charter-covenant question. A: not in M1b. Every redaction is visible to Squid, and the rule is decided before the first wake (checklist item 11) · B: yes; M1b refuses to redact `self` entries until M5 can record agreement. *Recommended: A. Tightening later costs nothing while the format is provisional.*

**Q20. What a redaction promises.** Redaction clears the text from the live record and from the database files on disk (B.5). **A:** "Removed from the live record, once cleanup completes, and from backups made after the redaction. Earlier backups and exports, disk snapshots and model-server logs may still hold it. Other entries that quote or restate it, and derived layers until they are rebuilt, are untouched unless they are redacted too. This is not erasure." **B:** A plus a documented procedure for clearing the text from old backups on the backup machine. *Recommended: A. B means editing the snapshots DESIGN 13 is built to keep unchanged.*

**Q21. Who besides you may ever run covenant commands?** Each covenant entry records who ran it. That is a claim, not a check (see the threat model in M1b). The real protection is structural: nothing the model can reach sets an entry's author. A: only you · B: you, plus people you name later (for example, a successor). *Recommended: A for now; revisit with DESIGN 16's "what happens if the user ever stops".*

- **Q11. The author label on Squid's own entries is `self`**, not DESIGN 3.1's `squid`. It is the word the record already uses for Squid's trust level and source type, and it keeps the fixture's test exports from saying "squid" (rule 2's aim). - **Q12. Seven additions to the record format**, each permanent after the first wake: (1) `data`: short structured facts (ids, counts, choices) that survive redaction, so covenant entries stay checkable. (2) Salted content hashes: without a salt, removed short text like "yes" can be recovered by guessing. (3) Confidence as a whole-number percent: decimals are written differently by different languages, which breaks hash checks. (4) `accesses`: how an access entry names each entry opened. (5) Source type `system`: harness entries need a source. (6) A version on every entry: old entries stay checkable if the format grows. (7) Links stored on the entry: no link can be added to an old entry later. Until the format review, format changes need no migration code: each bumps a version, regenerates the fixture, and still gets a DECISIONS line.
- **Q13. M1 scope.** (1) M1 is split into M1a (record core) and M1b (covenant commands). (2) `squid init --role fixture` is added to M1a: it creates a record and loads the fixture kit, since no ROADMAP milestone creates a record. `--role live`, the path that will create Squid's record before its first wake, isn't built in M1 at all (Q31), so Squid's record can't be created by accident. (3) Small additions: verify's `--db`, `--export`, `--anchor`, `--json` and `--list`; exit codes 3 (guard refusal) and 4 (cleanup incomplete); the instance marker and `record_meta`; `covenant list` (a metadata-only command-line aid, not a UI) and `covenant scrub`; `redact --show-related` and `--category`; `repair --action` and `--problem`; `--reason-file`; `export --include-private` (only if Q14 is A); `HASHING.md` in every export. (4) From M3 on, derived layers live in a separate file that isn't backed up, since it is rebuilt from the record. This keeps derived copies of text out of backups that can't be deleted, and lets the record file refuse schema changes.
- **Q22. `reasoning` gets the same audited access as private notes.** Rule 10 already says so; DESIGN 3.6, ROADMAP M1 and DECISIONS name only private notes, which wording fix 3 corrects. open-private covers both, and each access entry counts entries per channel. How the M2 prompts describe the reasoning channel to Squid is an M2 question.
- **Q30. Doc wording fixes 1–7** (listed under "Proposed wording fixes" below) are applied in one docs-only commit at the end of M0. Those that depend on a later answer (Q6, Q14, Q25) land when that answer comes. DECISIONS gets new dated lines, never edits.

### Kit format and `squid kit check`

A kit is a directory whose manifest lists every file; nothing is globbed. The fixture and your real kit use the same format (DESIGN 7.1).

| `kit.toml` key | type | rule |
|---|---|---|
| `format` | int | must be `1` |
| `entity_name` | string | matches `[A-Za-z][A-Za-z0-9 _-]{0,63}` (the same rule the record's first entry enforces) |
| `fixture` | bool | required, no default |
| `[speakers] user`, `[speakers] entity` | string | labels used on speaker lines; 1–32 printable characters, no `#` or `:`, no leading or trailing space; the two differ even ignoring case |
| `[files] charter`, `first_wake_letter` | path | required |
| `[files] seed_exchanges` | array of paths | at least 1, in ingestion order |

- **Paths:** relative, lowercase ASCII (`a-z 0-9 . _ -`), at most one directory level, ending in `.md`. No `..`, no leading `/` or `.`, and no two names equal ignoring case (APFS is case-insensitive). Each must be a regular file, never a symlink.
- **Turns** (pending Q4): a speaker line is exactly `## <label>`, using one of the two manifest labels, and a seed file's first non-blank line must be one. A turn runs to the next speaker line and must contain a non-blank line. Everything in it is kept byte-for-byte. Each exchange needs at least 2 turns, with both roles present. These lines are errors: any other line starting with `## `; a **near-speaker line**: up to 3 leading spaces, 1–6 `#`, optional whitespace, then a manifest label (compared ignoring case) followed only by whitespace; any line starting with `##` and then a character that is neither a space nor `#`. So `##Wren`, ` ## Wren` and `##<TAB>Wren` can't silently merge two turns.
- **Bytes**, checked before parsing, for every file including `kit.toml`: non-empty, not whitespace-only, at most 1 MiB, and strict UTF-8. **Rejected, never fixed:** a BOM, any CR, NUL, other C0 controls except TAB and LF, and RTF (`{\rtf`). The strict decoder accepts a BOM and NUL, so both get explicit checks (B.18). There is no Unicode normalization.
- **Directory:** every regular file must be listed. OS clutter (`.DS_Store`, `._*`, `Icon\r`) is never read, only counted. An unlisted file or directory, or a symlink anywhere, is an error.
- **Errors never echo text.** Each error is `path[:line[:col]] <error-class>`, with no free-text field: no kit text, manifest value, unknown key name or offending label. For TOML syntax errors, the line and column come from the regex `\(at line (\d+), column (\d+)\)$` on `str(e)`, because Python 3.12's `TOMLDecodeError` has no position attributes and its message echoes keys and characters (B.18). If the regex doesn't match, the error is `kit.toml manifest-syntax` with no position, and the message is discarded. Errors are collected (capped at 50) and sorted. Classes: `manifest-missing manifest-syntax unknown-key missing-key bad-type bad-value format-unsupported file-missing file-unlisted name-collision path-not-allowed symlink file-empty file-too-large not-utf8 bom carriage-return nul control-char rtf seed-no-leading-speaker unknown-speaker near-speaker-line empty-turn too-few-turns missing-role`.
- **`load_kit(path) -> Kit`** (stdlib only) returns frozen dataclasses: the manifest fields, each file's exact bytes and SHA-256, and each exchange's turns as (role, first line, last line) spans into the unchanged bytes. Every byte and text field uses `field(repr=False)`, so a traceback or debug print can't show kit text. It never rewrites text, writes to disk, follows symlinks or touches a data dir. M1a's `init` calls it.
- **`squid kit check PATH`** prints the format version, the fixture flag, file and seed counts, turns per role, each file's byte length and SHA-256, and a kit digest (SHA-256 of the canonical JSON of the manifest-ordered `[path, sha256]` list). It never prints `entity_name` or any other text. Exit codes follow the CLI table in M1a (0 valid, 1 invalid kit, 2 usage or I/O).

### The format in brief (full reference: Appendix A)

- **Tables.** One `entries` table (STRICT) with 20 columns. 17 are covered by `entry_hash`; `content` and `content_salt` are not, so a redaction can clear them without breaking the chain. `links` is a trigger-filled projection of each entry's hashed `links` array, and `record_meta` is a write-once mirror of the first entry's `data`. Both can be regenerated from entries: before the freeze by rebuilding the record, after it only through the migration mode (the round-trip loader tests this). Nothing else lives in the record file; derived layers get their own file from M3 on (Q13), so the authorizer can forbid `CREATE` and verify can demand an exact schema.
- **Seq 1 is a genesis `system_event`** with `data = {event:"genesis", record_id, role, entity_name, schema_version, hash_version, harness_version}`, `prev_hash` of 64 zeros, and empty content (the harness writes no prose). It can never be redacted.
- **Trust is always computed** from (author, source.type), lowered to the least-trusted `derived_from` target. Callers can't pass it (A.3).
- **Three version numbers:** entry `v` (which fields the hash covers), `hash_version` (canonicalization and hash function), and `schema_version` (the SQLite layout, also `PRAGMA user_version`). In v0 they are 0, 0 and 1. Entries the harness writes also carry `harness_version` in `data`.
- **Order is `seq` alone**, never id or ts. `session_id` is always null in M1.

### IDs, time and entropy

- **Clock and entropy.** `Clock.now_ms() -> int` is `SystemClock` in production and `FixedStepClock(start_ms, step_ms)` in tests. `Entropy = Callable[[int], bytes]` is `os.urandom` in production. Tests use `CounterEntropy(seed)`: one byte stream, consumed in order across calls, made of SHA-256(seed ‖ 8-byte big-endian counter) blocks with the counter starting at 0. Python doesn't promise `randbytes` stays the same across versions, and golden vectors must survive upgrades and be reproducible in another language (B.12).
- **Per append**, one `now_ms()` read supplies both `ts` (`YYYY-MM-DDTHH:MM:SS.mmmZ`) and the ULID time. The in-repo ULID generator (about 35 lines) draws 10 bytes when the millisecond advances and otherwise adds 1 to the previous randomness, per the ULID spec; then 16 bytes are drawn for the salt.
- **Priming.** The generator is primed from the head id when the writer opens, so ids keep increasing across restarts and backward clock steps; a trigger enforces `id > head id`. `ts` records the real clock reading, never clamped. verify warns (without failing) on a ts regression or a ULID time that differs from ts. It reports this once per contiguous run of such entries (first and last seq, maximum skew), because one bad forward reading pins later ULID times until real time catches up (B.29).
- **Live records refuse test inputs.** `RecordWriter.open` reads `record_meta.role`. For `live` it accepts only `SystemClock` and `os.urandom`: salts from a known seed can be replayed, which would expose redacted short text (B.29). The CLI exposes neither parameter.

### Append API

```python
class RecordWriter:
    @classmethod
    def open(cls, data_dir: Path, *, clock: Clock, entropy: Entropy) -> "RecordWriter": ...
    def append(self, *, author: Author, channel: Channel, kind: Kind | None,
               confidence: int | None, source: Source, links: Sequence[Link],
               session_id: str | None, model_id: str | None,
               prompt_versions: Mapping[str, str], data: Mapping[str, JSONValue],
               content: str) -> Entry: ...
    def transaction(self) -> ContextManager[Txn]: ...  # Txn.append has the same signature
```

Every parameter is keyword-only with no default, checked by a test with `inspect.signature`. So a field counts as stamped only when the caller passed it, even as an explicit null (rule 5). The enums are `StrEnum`s from `vocab`, and `Source` and `Link` are frozen dataclasses with every field required. Callers never pass `v`, `seq`, `id`, `ts`, `trust`, `content_salt`, `content_hash`, `prev_hash` or `entry_hash`. `append()` is a one-entry transaction, and within one transaction a later append may link to an earlier one. `repr(Entry)` never includes content.

1. Validate the draft without the database: enums, matrix row, kind and confidence, source shape, links (sorted; duplicates rejected, not dropped), `data` shape, and content that encodes as UTF-8 with no NUL.
2. `write_txn()`: check that the lock is still attached (below), `BEGIN IMMEDIATE`, then read the head `(seq, id, entry_hash)` inside the transaction.
3. Check that link targets exist, read the trust of each `derived_from` target, and compute trust.
4. Read the clock, make the id, draw the salt, and compute `content_hash`, the preimage and `entry_hash`.
5. `INSERT` with seq = head+1 and prev_hash passed explicitly. An omitted seq shows up as −1 in the trigger (B.2).
6. The BEFORE INSERT triggers re-check every rule they can; the AFTER INSERT trigger fans out the links.
7. Read the row back and recompute `entry_hash` from the stored values, which catches type-affinity drift.
8. `COMMIT`; on any exception `ROLLBACK`. seq stays gapless after a rollback (B.2).

### Triggers and the authorizer

Twelve triggers (A.5) enforce: append-only for all three tables; gapless seq and the chain; unique seq, id and entry_hash (this closes `INSERT OR REPLACE`, `REPLACE INTO` and UPSERT, which otherwise delete rows without firing the delete trigger; B.1); the provenance and rel matrices, and computed trust; links that exist only as the head entry's mirror; write-once `record_meta`; one narrow UPDATE shape for redaction.

Enums live in trigger SQL, not in CHECK constraints: a CHECK also applies to UPDATE (it would block the redaction path), and changing one means rebuilding a table that must never be rewritten. Before the first wake, a new enum value means regenerating the fixture. After it, it needs an explicit migration mode that recreates the trigger and appends a `system_event`.

**Every trigger check is NULL-safe** (B.25). A plain `WHERE NOT (pred)` passes when `pred` is NULL, which a missing or null JSON key produces. So: checks are written `WHERE NOT coalesce((pred), 0)`; key presence is tested with `json_type(x,'$.k') IS NOT NULL`, and booleans with `json_type(...) IN ('true','false')`; comparisons on JSON extractions use `IS`; `source` must have exactly the key set `ref,title,type,url`, compared with `IS` against the ordered `group_concat` over `json_each`; `source` and `data` may not hold duplicate keys (count vs. count of distinct keys over `json_each`). SQLite reads the first duplicate and Python the last, so triggers and verify could otherwise see different values.

**What triggers can't do:** anything that can write the file can drop them (B.3). They guard against bugs and careless clients. Integrity rests on the hash chain, verify (including its schema check), anchors from older backups (DESIGN 3.4, 13) and OS permissions (DESIGN 12).

The writer's **authorizer** (B.4) has modes `init` and `normal`, plus `redact` and `scrub` in M1b. It is installed after the profile's own pragmas are set. Every mode denies DROP, ALTER, ATTACH, DETACH, and inserts into `links` from anywhere but the fan-out trigger. `CREATE` and pragma writes are allowed only in `init`. UPDATE and DELETE on the three tables are denied, except that `redact` allows one top-level UPDATE of `content` and `content_salt`. `redact` and `scrub` also allow exactly `PRAGMA wal_checkpoint(TRUNCATE)`.

### Connection profiles

| setting | writer | readers (verify, export, covenant list) |
|---|---|---|
| opens | only after the lock, file and marker checks (below) | never the live files while a writer could run (below) |
| transactions | `autocommit=True` plus `write_txn()` (B.8) | all reads in one `BEGIN`…`COMMIT` (one snapshot) |
| journal_mode | WAL, set at init, then asserted | never set (B.6) |
| synchronous=FULL, fullfsync, checkpoint_fullfsync | on (the last two are no-ops on Linux; **Mac-unverified**) | — |
| secure_delete=ON, recursive_triggers, foreign_keys | on (per connection, not persisted; uv's SQLite defaults secure_delete OFF, B.5) | — |
| DEFENSIVE; query_only | DEFENSIVE on | both on |
| checks at open | SQLite ≥ 3.38 (B.13); triggers enabled; user_version 1; pragmas read back; **`sqlite_schema` equals the expected rows** (verify check 2), else exit 3 | SQLite ≥ 3.38, user_version |

**Readers never modify any file or leave new ones** (B.26). In data-dir mode, a reader takes `flock(LOCK_SH|LOCK_NB)` on `record.lock`, opened read-only. If a writer holds the lock, it exits 3 ("record in use; run it while Squid rests", Q15). If `record.lock` is absent, as in a restored copy, nothing is created. With no `-wal` beside the database, the reader opens the original with `mode=ro&immutable=1` and holds the shared lock for the whole read. With a `-wal` beside it (a crash, or a file-level copy of a live dir), the reader copies the database and its `-wal` into a fresh 0700 temp dir under the shared lock. It opens that copy with `mode=ro` and deletes the temp dir afterwards; the original is never opened. Copy mode (`--db FILE`) follows the same rules without a lock. A `-journal` beside the file means it isn't a record this harness wrote (exit 2). Afterwards, the reader re-stats the original and exits 2 if anything changed during the run.

The cost is that readers, like the covenant commands, can't run while Squid is awake (Q15). A writer starting while a reader holds the shared lock gets exit 3, and M5 retries. URIs are built with `Path.resolve().as_uri()`, because naive `file:` strings lose `mode=ro` on paths containing `#` or `?` (B.7).

### Single-writer lock and instance marker (rule 7)

- **Lock:** `<data>/record.lock`, created 0600, opened with `O_NOFOLLOW`, and locked with `flock(LOCK_EX|LOCK_NB)` before the writer connection opens, then held for the process lifetime. Never `lockf`, and never lock the db file: SQLite holds POSIX locks there, which drop when any descriptor on the file closes (B.9). The file's `{pid, host, started_at}` is informational only.
- **A lock is never stale.** The kernel releases a flock when its holder dies. So the README says never to delete `record.lock`: flock locks the inode, and after an unlink a second process can lock a fresh file (B.9). `write_txn()` checks that the lock is still attached: `fstat(fd).st_nlink > 0` and `(st_dev, st_ino)` equal to `stat(record.lock)`. Otherwise it exits 3.
- **Inheritance.** The lock fd is non-inheritable (Python's default; a test asserts `os.get_inheritable(fd)` is False), and only the holder ever releases it. A long-lived child that inherited it would keep the lock after the parent died (B.9).
- **Second paths.** Writers refuse (exit 3) if `record.sqlite3` is a symlink or has `st_nlink ≠ 1`. A hard link in another directory would otherwise get its own `record.lock`, and with it a second writer (B.24).
- **Instance marker.** `<data>/instance.json` (0600) holds `{record_id, created_at, dir_ino, db_ino, volume, machine}`. init writes it after the record commits. `volume` and `machine` are read through `fsutil`: on macOS the volume UUID and hardware UUID (**Mac-unverified**), on Linux (development only) `st_dev` and the hostname. Every writer requires the marker. Its `record_id` must equal `record_meta.record_id`, and every identity field must match the current files. SQLite writes the database in place and never replaces it, so its inode survives appends, redaction, checkpoints and VACUUM (verified). A whole-directory copy (`cp -a`, a Finder duplicate, a Time Machine or Migration Assistant restore) gets new inodes, so its writers refuse (exit 3) while verify still works (B.24). M7 also keeps the marker out of the backup set. A deliberate move to another volume or machine is a recorded re-bind through the same path as promotion (Q25). Nothing hashed changes. **Remaining limits:** anyone who can write the data dir can forge a marker. A block-level clone of a whole volume may keep inode numbers; the volume and machine identity narrow that.
- **Writer open order:** resolve the data dir → check modes (dir 0700, files 0600; refuse if looser) → lock → database not a symlink and one link → marker and identity → open the writer → exact schema check → compare record_id → role check for Clock and Entropy.
- **Data dir:** `--data-dir` or `SQUID_DATA_DIR`, with **no default**. Neither given, or both given and different → exit 2. It must be on a local filesystem (flock over SMB or NFS is unreliable). File modes: data dir 0700; db pre-created 0600 with `O_EXCL`, so `-wal`/`-shm` inherit 0600 (B.19); lock, marker and export files 0600.
- **Containment checks** never compare string prefixes. They cover "inside a git work tree", "under `dev/fixture/` or the temp dir", "inside the exports folder" and the cloud folders. Each check resolves both sides, walks the candidate's resolved ancestors, and tests `os.path.samefile` against the resolved root. On macOS the temp dir resolves under `/private/var`, and APFS ignores case (B.23). The cloud-folder check runs against both `Path.home()` and the account's `pwd` home.

### `squid init --role fixture` (scope addition, Q13)

`squid init --role fixture --kit PATH [--data-dir DIR]`. `--role` is required, and `live` exits 2 ("not available in this version"); the Python create function accepts only `fixture` in M1. The kit is loaded by M0's loader; it must say `fixture = true` and sit under the repo's `dev/fixture/` or the system temp dir. The data dir must be absent or empty (else exit 3), and outside any git work tree.
1. Validate the whole kit → create the data dir 0700 → create and flock `record.lock` → pre-create `record.sqlite3` 0600 with `O_EXCL` → open the writer in `init` mode (no marker check yet) and set WAL.
2. In one `BEGIN IMMEDIATE`, write the DDL and triggers, `user_version = 1`, genesis, the `record_meta` rows, then the founding entries: charter, first-wake letter, then seed exchanges in manifest order. Each founding entry has author `user`, channel `founding`, source `user`, trust computed as `trusted`, model_id and session_id null, and `data` per A.2. Its content is the exact file text (per Q5 A; one entry per exchange). Then COMMIT.
3. Write `instance.json` (fsync the file and the directory). Print `record=<id> role=fixture entries=N head=<seq>:<hash>` and nothing else.

A crash before COMMIT leaves an empty db and no marker, so writers refuse. init never deletes anything, and a rerun needs an empty dir. Founding entries have a null session_id: the kit is ingested before the first wake, which is an ordinary session (DESIGN 7.1; DECISIONS 2026-09-23). **Fixture regeneration** runs the same path with `FixedStepClock(2026-01-01T00:00:00.000Z, 1000 ms)` and `CounterEntropy(b"fixture-v0")`. The resulting `(seq, id, entry_hash)` list and head are committed as `tests/record/golden/fixture_v0.json`; a database is never committed.

`squid verify (--data-dir DIR | --db FILE | --export DIR) [--anchor SEQ:HASH]... [--json]`. `--db`, `--export`, `--anchor` and `--json` are Q13 additions, and M1b adds `--list`. It is a reader only: it never writes, and never modifies or creates a file (see "Connection profiles").

| # | check | db | export |
|---|---|---|---|
| 1 | SQLite ≥ 3.38; user_version or manifest versions known (unknown → exit 2) | ✓ | ✓ |
| 2 | `sqlite_schema` rows (type, name, tbl_name, sql) match exactly: catches a dropped or altered trigger or an extra table | ✓ | — |
| 3 | `PRAGMA integrity_check` | ✓ | — |
| 4 | genesis shape at seq 1; `data.record_id` = its id; `record_meta` (or manifest) equals genesis `data` | ✓ | ✓ |
| 5 | seq is 1..N with no gaps or duplicates; ids strictly increase | ✓ | ✓ |
| 6 | per entry: stored JSON is canonical (no duplicate keys); enums, matrix row, kind/confidence, source key set, private-channel source fields and `data` shapes valid; trust recomputes | ✓ | ✓ |
| 7 | every prev_hash links to the previous entry; every entry_hash recomputes | ✓ | ✓ |

Output is check names, seq, ids, hashes, counts, record_id, role and versions only; never content, `data` strings, source titles or URLs. Summary line: `ok|FAIL record=<id> role=<role> entries=N head=<seq>:<hash> redacted=R withheld=W warnings=K`; `--json` has the same fields.

### `squid export`

`squid export --out DIR (--data-dir DIR | --db FILE)`. It is a reader: it opens the record like verify and reads everything in one transaction, so the manifest's head matches the rows.
- **`entries.jsonl`:** one canonical JSON object per record in seq order, holding all 20 stored fields plus an unhashed `content_state`. Records are separated by the byte 0x0A only (UTF-8, no BOM). Content may contain U+2028, U+2029 or U+0085, so readers must not split on those; Python's `str.splitlines` does (B.10). `HASHING.md` and the README say so.
- **`content_state` is derived per row:** `present`: content and salt present. `redacted`: both NULL, plus exactly one valid `redacts` link from a redaction entry. `withheld`: the channel is in `PRIVATE_CHANNELS`, and this export withheld the text (or it was already absent). Any other state makes export refuse (exit 1) and remove its temp dir.
- **`HASHING.md`:** a byte copy of the spec in A.4, enough to recompute every hash without this code.
- **`manifest.json`** (written last): `format: "squid-record-export"`, `export_version: 0`, `record_id`, `role`, `entity_name`, `entry_format_v`, `schema_version`, `hash_version`, `head_seq`, `head_hash`, `entry_count`, `counts_by_channel`, `counts_by_author`, `redacted_count`, `withheld_count`, `withheld_channels`, `files` ({name: {bytes, sha256}}), `sqlite_version`, `harness_version`, `exported_at` (from the Clock).
- **Private content (Q14):** `content` and `content_salt` of `private_note` and `reasoning` entries are withheld. Their hashes stay, so the chain verifies. M1a has no flag to include them.
- **Where it writes:** `--out` must not exist. Files are built in a fresh 0700 sibling temp dir, created `O_EXCL` 0600 and fsynced (`F_FULLFSYNC` on macOS). The directory is fsynced and renamed to `--out` at the end; on any failure the temp dir is removed. Exporting twice with the same Clock gives byte-identical files. Export refuses (exit 3): an `--out` inside any git work tree (the same check as init); on macOS, paths under `~/Library/Mobile Documents`, `~/Library/CloudStorage`, `~/Desktop` or `~/Documents`, because iCloud sync can't be detected reliably (Mac-unverified); for a record whose role is `live`, any `--out` outside the `exports/` folder in the home of the account that owns the data dir. The deny rule covers that folder, M7 creates it, and there is no override flag.
- **Round trip, with no import command:** (1) Export, then `verify --export`, which is clean. (2) A test-only loader bulk-inserts in seq order and only then creates the triggers (redacted rows would otherwise be refused). (3) `verify` on the loaded db exits 1, with check-8 "content missing" findings at exactly the seqs the manifest lists as withheld; it passes every other check. (4) Re-export, byte-identical to the first. The round-trip fixture contains at least one redacted row (made with the test helper), one withheld `private_note`, a founding entry with the non-ASCII seed text, golden vector 0's content, and a `derived_from` link. The loader's rebuilt `links` and `record_meta` are compared with the originals.

**Commits:** (1) Vocabulary, canonical JSON and hashes: golden vector 0, a second serializer, type rejections. (2) Clock, entropy, ULID: spec vectors, priming, pinned `CounterEntropy` bytes, live-role refusal. (3) Schema and triggers from vocab: the raw-SQL attack suite (A.5). (4) Connection profiles and authorizer: reader paths, the writer's schema check. (5) Lock and marker: subprocess tests, `conftest.py`, `test_env_isolation.py`. (6) Append API: matrix, signature test, grep test. (7) `init --role fixture`: genesis, ingestion, file modes, fixture golden vectors. (8) verify: all modes, tamper suite, no-modification tests, canaries. (9) export and `verify --export`: test loader, round trip, export tamper cases. (10) Docs: README, CLAUDE.md Commands, DECISIONS lines, first-wake checklist items.

### Tests and done-when

**ROADMAP done-when → tests:** updates and deletes are rejected → `test_append_only.py` (every attack in A.5 on all three tables, on a raw connection with recursive_triggers OFF and ON, then through the writer; rows byte-identical afterwards); tampering is caught → `test_verify_tamper.py`; a second writer is refused → `test_lock.py`, `test_instance.py`; export round-trips → `test_export.py`; redaction leaves a verifiable chain → `test_redaction_states.py`, via a test helper that runs M1b's two statements; rule 1 → `test_env_isolation.py`.

**Tamper cases, database** (on a `VACUUM INTO` copy; each exits 1 and names the check): edited content; an edited hashed field; an edited entry with its own hash recomputed (the break shows at the next prev_hash); a deleted middle row; a deleted tail with the triggers recreated exactly (plain verify exits 0, `--anchor` exits 1); content nulled without a redaction; a forged links row; non-canonical stored JSON; a duplicate key in `data`; an enum violation after dropping triggers; with triggers dropped and the hash recomputed: a source with a renamed key, or a covenant entry with no `data.event` (check 6); record_meta ≠ genesis; a changed salt; a changed genesis prev_hash; a dropped trigger with no data change.

**Tamper cases, export:** a non-private row stripped and labelled `withheld`, with the manifest rewritten; `present` relabelled `redacted` without a link; content present but labelled `withheld`; the last line deleted with the manifest rewritten (exit 0 without `--anchor`, 1 with it); edited manifest counts.

**Second writer** (real subprocesses). While one process holds the lock, another process's writer exits 3, and a second open in the same process is refused. Two concurrent inits into one empty dir: one succeeds, the other exits 3. After the holder is SIGKILLed, the lock is free. Unlinking the lock file under a holder makes the holder's next append exit 3. The lock fd is non-inheritable, and a holder that spawns a long-lived child and is then SIGKILLed leaves the lock free. The writer refuses (exit 3) a `VACUUM INTO` copy in a fresh dir (no marker) and a `cp -a` copy of a data dir (marker present, identity different); verify exits 0 on both. Exit 3 also for: a hard-linked or symlinked `record.sqlite3`; a marker naming another record_id; a group- or world-readable data dir; a record with a dropped trigger (the writer refuses to open); a non-empty data dir for init.

**Determinism:** Golden vector 0 agrees between Python's `json` and a hand-written serializer. The Node agreement in B.10 was a one-off prototype check, not a test. The canonicalizer rejects floats, NaN, non-ASCII keys, duplicate keys, lone surrogates and integers ≥ 2^53. The ULID spec vectors pass, and `CounterEntropy`'s first bytes are pinned. Two fixture builds with the same Clock and seed are identical, a different seed changes ids and salts, and `fixture_v0.json` matches.

**No modification:** verify and export leave each of the following byte-identical (names, sha256, mtimes), with no new files: a quiesced data dir, a `VACUUM INTO` copy, a backup-API copy, a data-dir copy with a `-wal` from a SIGKILLed writer, and an export dir. While a writer holds the lock, `verify --data-dir` exits 3.

**Other:** Every author × channel × source.type × model_id-null combination is accepted exactly when it is a matrix row, by the API and by raw insert. Every rule that reads `data` or `source` is tried with the key missing, JSON null, the wrong JSON type (`"true"`, `1`) and a duplicate key. Pragma read-back, and authorizer denials. URIs containing `#`, `?`, space, `%` and non-ASCII. `st_mode` under umask 022, and containment under a symlinked TMPDIR. A live-role record (built by a test-only helper) refuses `CounterEntropy` and `FixedStepClock`, and refuses an export outside an injected exports folder. Canaries in private_note, reasoning, conversation and journal entries never appear in verify output, errors or the manifest, and the private ones appear in no export byte. A canary in a private note's `source.title` is refused at append, without being echoed. These are refused: `--role live`, a `fixture = false` kit, a kit outside the allowed places, a data dir inside the repo, and an export `--out` inside the repo.

**Done when:** all of the above pass in `scripts/check`, and `init --role fixture` on the fixture kit, then `verify`, `export` and `verify --export`, all exit 0 on a temp dir. The first-wake checklist items for M1a are written.

**Prototype status:** A first v0 prototype (uv CPython 3.12.11, SQLite 3.50.4, Linux) passed 131 checks, all for M1a: triggers, the attacks then listed in A.5 with recursive_triggers OFF and ON, malformed inserts, the redaction path, the main tamper cases, golden vector 0, determinism, both reader modes, file modes and the lock. It had no missing-key or NULL cases, and it counted the round trip's check-8 finding as a pass. A review prototype then found the gaps this version fixes (B.24–B.29). The NULL-safe predicates, the key-set and duplicate-key checks, the inode-bound marker and the non-modifying reader paths were re-checked by experiment. Not validated: anything on macOS, the CLI wiring, the HASHING.md wording, the kit loader.

## M1b: Covenant commands

**Goal (ROADMAP M1; DESIGN 3.5, 3.6):** the four commands through which you change or read Squid's record. Each appends an entry that Squid can see and that carries your reason. Only the audited ones display private content. The code lives in `squid/covenant/` and writes through M1a's writer. **Waits on:** M1a being done, and Q15–Q21 (Q22 is decided). The defaults below assume the recommended answers.

### Rules shared by all four

- **Invocation:** `squid covenant <cmd> --data-dir DIR` (or `SQUID_DATA_DIR`). In production you run it as Squid's account, `sudo -u ACCOUNT squid covenant …`, with a password. The checklist confirms sudo records no I/O for these commands.
- **Preconditions** follow M1a's writer order: modes, lock, marker. The lock is taken **before any prompt**, so you never type a reason for a command that can't run. It is held until exit, so nothing changes between confirmation and commit. If the lock is held, the command exits 3 and prints the lock file's pid, host and start time. It doesn't wait or queue (Q15).
- **Reasons are never command-line arguments.** An argument lands in shell history, is visible to every account through `ps`, and is copied into sudo's log. A reason, or a correction's text, is read from a prompt on `/dev/tty` (lines until a lone `.` or EOF) or from `--reason-file PATH` (`-` for stdin; under sudo, `--reason-file - < file` lets your shell open the file).
- **Warning** printed before every reason prompt (shown, never stored; you approve the wording): the reason is permanent, stored in Squid's record and visible to Squid. Some commands add a line: `redact`: the reason must not contain or hint at the removed content. `open-private`: the access itself (who, when, why, which entries) is recorded where Squid can see it. `correct` on a private target: this correction is not private; don't quote the private text (Q18).
- **Validation** uses M0's byte rules: strict UTF-8, no NUL, CR or controls except LF and TAB, not blank; a reason at most 2,000 characters, a correction at most 20,000; nothing normalized. Errors name only the class (`reason-empty`, `reason-too-long`, `reason-control-char`, …).
- **Confirmation:** after the targets are listed, you type `<verb> <n>` (for example `redact 3`) on `/dev/tty`. There is no `--yes`. Without a terminal the command exits 2, so nothing unattended can drive it. This is a speed bump, not authentication. Tests inject a fake Prompter and Confirmer through the Python API; the CLI has no flag for either.
- **Display is metadata only:** seq, id, ts, author, channel, kind, content length in bytes, state (present or redacted), and existing covenant links (corrected, accessed n times, repaired). The only exceptions are open-private's stdout and, if Q14 is A, the `--include-private` export files.
- **`squid covenant list [--channel C] [--author A] [--since TS] [--until TS] [--limit N]`** (Q13) is a reader that prints metadata in the same format, so you can find ids without reading content before M8.

**Entry shapes** are in A.2. Every covenant entry has author `user`, trust `trusted`, source `{type:"user", ref:null, title:null, url:null}`, and a `data` field holding `event`, `operator`, `operator_authenticated: false` and `harness_version`. `content` holds only text you typed. Targets live only in the hash-covered links, and `data.targets` is a count that verify checks against them. **`operator`** is a role enum, `{user}` in M1 (Q21). It records who ran the command, as claimed. It is not the OS login, because `data` is permanent and a login is often a personal name.

**Threat model** (a DECISIONS line): any code running under Squid's account, such as a harness bug or a compromised dependency, could write entries that look like covenant entries by opening the file directly, and only a comparison with backups would show it. What matters is structural: no path the model uses can set `author` or `trust` (tested in M5).

### `correct` and `repair`

**`squid covenant correct --target ID [--target ID …]`** (DESIGN 3.5; DESIGN 5, item 7) works in one transaction. It re-checks the targets: each must exist and be neither genesis nor redacted, and a private target needs an earlier access entry covering it (Q18). Then it appends one `annotation` with `corrects` links and commits. The original stays untouched. No derived layer applies a correction automatically, because Squid checks it (DESIGN 5). Plain comments (`annotates`) and Squid's replies come later (M8).

**`squid covenant repair --target ID … --action A --problem P [--duplicate-of ID]`** appends one `system_event` with `repairs` links; your description of what went wrong is the typed text. `action` ∈ {`suppress`, `note`, `revoke`}; `problem` ∈ {`duplicate`, `wrong_provenance`, `harness_bug`, `other`}. `duplicate_of` is given only for suppress+duplicate. It must exist, come before every target, and not itself be a target. `revoke` takes exactly one target: an earlier repair that isn't already revoked. Raw entries stay as they are. `author=system` stays reserved for automatic repairs, and v1 has none. A repair never changes verify's verdict: a broken chain can't be annotated away, and fixing one means restoring from backup (M7).

### `redact` and `scrub`

`squid covenant redact --target ID … [--blind-private] [--category C] [--show-related]`
1. Preconditions and the lock, then resolve the targets with a read. The whole command is refused (exit 1, nothing written) if any target is unknown, genesis, already redacted, an access entry or a founding entry (Q16). Private targets need `--blind-private` (Q17).
2. Show the metadata. `--show-related` also lists, as metadata, entries linked to or from the targets and entries from the same session, which you can then add as more `--target`s. Paraphrases elsewhere can't be found this way.
3. Show the warning, then read the reason and the `category` (`third_party_privacy`, `user_privacy`, `harness_error`, `other`), then the confirmation `redact N`.
4. One `BEGIN IMMEDIATE` on a writer in `redact` mode: (1) Re-resolve the targets and compare them with the confirmed set. (2) Assert `PRAGMA secure_delete` reads 1 **on this connection**. (3) Append the redaction entry. (4) Run `UPDATE entries SET content=NULL, content_salt=NULL WHERE id IN (…)` and assert the row count is N. (5) `COMMIT` (synchronous=FULL). The trigger admits the UPDATE because the `redacts` links were inserted earlier in the same transaction. Any failure rolls everything back, so there is never a half-done state.
5. Residue cleanup: `PRAGMA wal_checkpoint(TRUNCATE)`, retried for about 10 s. It is complete when the result is `(0,0,0)` and the `-wal` is 0 bytes. Otherwise exit 4: "committed; cleanup incomplete; close any running verify or export, then run `squid covenant scrub`".
6. Print the new entry's seq and id, the count redacted, and the cleanup status. The reason is not echoed.

**`squid covenant scrub`** takes the lock, runs the TRUNCATE checkpoint, and exits 0 if clean or 4 if not. It appends nothing.

**Verified by experiment (B.5):** with secure_delete ON on the nulling connection and TRUNCATE returning `(0,0,0)`, the db, `-wal` and `-shm` held 0 copies of canaries in a 0.4 KB private note and a 40 KB reasoning entry (overflow pages), and verify passed. Any open reader makes the checkpoint report busy, conservatively even when the db is already clean. With secure_delete OFF on the nulling connection, 13 and 2,469 copies remained even though the checkpointing connection had it ON.

### `open-private`

`squid covenant open-private --target ID …` (DESIGN 3.6, rule 10)
1. Refuse (exit 2) unless stdout is a terminal. There is no `--out` and no pager, so the terminal holds the only copy.
2. Lock, then resolve the targets. Each must be in `PRIVATE_CHANNELS = {private_note, reasoning}` (Q22) and not redacted. Non-private ids are refused rather than opened, so the audit lists only what the covenant covers.
3. Metadata, the warning, the reason, then the confirmation `open N`.
4. One transaction: re-resolve the targets, append the access entry (`accesses` links; `data.channels` counts per channel), `COMMIT`. synchronous=FULL (plus fullfsync on the Mac) makes the commit durable before it returns.
5. **Only after COMMIT returns** are exactly the linked ids read and written to stdout, each after a metadata header. The lock is still held, so nothing can change them. Control characters other than LF and TAB (C0, including ESC, and C1) are shown escaped, so stored text can't drive the terminal.
6. A failure before the commit prints nothing. A failure after it leaves the access entry standing: a record of an access that showed nothing is acceptable, content shown with no record is not. One run makes one access entry, only metadata goes to stderr, and nothing is logged.

**`squid export --include-private`** (if Q14 is A) is a writer. It reuses steps 2–4 with `data.output = "export"` and the same reason input, with three differences: the export is first built in its temp dir under the lock, so it can't change. The access entry records the manifest's sha256 in `data.manifest_sha256` and commits before the dir is renamed into place. `--out` must lie inside the exports folder in Squid's home, whatever the role. The warning says every later read or copy of these files is unaudited (Q14).

### Trigger, authorizer and verify additions

The tightened rel rules are in A.3, all NULL-safe (M1a). Each covenant `event` carries only its own rel, with at least one link of it. Targets must have content present. `redacts` may not point at genesis, an access entry or a founding entry. The redaction-only UPDATE trigger also requires the redacting entry's `data.event` IS `"redaction"`.

A second redaction of the same target already rolls back (verified). The authorizer gains `redact` and `scrub` modes (see M1a). verify's check 8 gains these states; output is still ids, seq and counts only, and `--list` adds target seq → redacting seq:

| state | condition | reported | exit |
|---|---|---|---|
| redacted | content and salt both NULL; exactly one valid `redacts` link from a `redaction` entry | info (count) | 0 |
| redaction incomplete | a valid `redacts` link, but content or salt present (only a bug or tampering: one transaction can't crash halfway) | error | 1 |
| partial | exactly one of content and salt is NULL | error | 1 |
| content missing | content NULL with no valid `redacts` link | error | 1 |
| over-redaction | two `redacts` links to one target; a link to genesis, an access entry or a founding entry | error | 1 |
| covenant malformed | an `event`, `action`, `problem`, `category` or `operator` missing or outside its enum; `targets` ≠ number of links; a bad `duplicate_of` or `revoke` | error | 1 |
| covenant activity | valid corrections, repairs, redactions, accesses | info: counts per event; accesses as "E events, M entries" per channel | 0 |

For a redacted entry, verify checks only that `content_hash` is well formed; with the salt gone it can't be recomputed, but `entry_hash` still covers it. `verify --export` recomputes the same states (M1a check 8). Residue on disk is outside verify's job; only `redact` and `scrub` report it.

**What redaction does not achieve.** Q20 is the promise, stated to you, in DECISIONS and in whatever wording Squid is shown. Behind it: truncating the `-wal` frees SSD blocks without overwriting them, and APFS or Time Machine snapshots keep copies (Mac-unverified). `--show-related` finds linked neighbours, not paraphrases. The metadata stays: seq, ts, author, channel, kind, links, `data` and `source` (Q28). So does the redaction entry, with its claimed operator, time, category, targets and reason (unless that is redacted too). The gap is meant to be visible (DESIGN 3.5). There is no undo; restating the text makes a new entry. The remaining hash reveals nothing only because of the salt (Q12). Audited access is tamper-evident only against backups taken after the access, and shown content lives in terminal scrollback, which macOS Terminal can save (Mac-unverified).

### A.4 Canonical hashing (the content of `HASHING.md`)

1. **content_hash** = lowercase hex SHA-256 of `salt ‖ content_utf8`, where `salt` is the 16 raw bytes whose hex is `content_salt` and `content_utf8` is the exact UTF-8 of `content` (no normalization, no BOM). For empty content only the salt is hashed.
2. **Preimage:** a JSON object with exactly 17 keys: `author channel confidence content_hash data id kind links model_id prev_hash prompt_versions seq session_id source trust ts v`. Every key is always present, never omitted: null for unset scalars, `{}` and `[]` for empty objects and arrays. It excludes `content`, `content_salt` and `entry_hash`. `source`, `links`, `prompt_versions` and `data` appear as JSON values, not strings.
3. **Canonical bytes:** RFC 8785 (JCS), restricted to a subset that every JCS implementation serializes identically. Values are null, true, false, strings, integers within ±(2^53−1), arrays and objects. Floats, NaN and Inf are rejected, and booleans are not integers. Integers are plain decimal. There is no whitespace. Object keys are ASCII, unique and sorted by code point. In strings, `"` becomes `\"` and `\` becomes `\\`. U+0008/09/0A/0C/0D become `\b \t \n \f \r`, and any other U+0000–U+001F becomes `\u00xx` (lowercase hex). Everything else, including U+007F, U+2028 and non-BMP characters, is literal UTF-8. Lone surrogates are rejected. In Python: `json.dumps(o, sort_keys=True, separators=(",",":"), ensure_ascii=False, allow_nan=False).encode()` after a type check.
4. **entry_hash** = lowercase hex SHA-256 of the canonical bytes. **Chain:** `prev_hash` of seq 1 is `"0"*64`; after that it is the previous entry's `entry_hash`.
5. JSON columns are stored canonically. verify re-parses and re-canonicalizes them, never trusting the stored text.
6. In an export, records are separated by the byte 0x0A only. Don't split on U+2028, U+2029 or U+0085.

### A.5 Triggers and the attack suite

Every predicate is NULL-safe (M1a, "Triggers and the authorizer").

| trigger | rejects |
|---|---|
| `entries_bi_chain` (BEFORE INSERT) | an existing seq, id or entry_hash (closes OR REPLACE, REPLACE INTO, UPSERT, OR IGNORE, whatever recursive_triggers says); seq ≠ head+1; prev_hash ≠ head hash; an id that isn't a ULID or is ≤ the head id; content or salt NULL at insert; a malformed salt, hash or ts; v ≠ 0 |
| `entries_bi_provenance` (BEFORE INSERT) | a source whose key set isn't exactly `ref,title,type,url`; duplicate keys in `source` or `data`; a combination not in A.3 (which also catches unknown enums); bad prompt_versions; kind or confidence out of place; non-object `data`; genesis anywhere but seq 1, or malformed; a non-null session_id (M1); in `PRIVATE_CHANNELS`, a non-null `source.title` or `source.url`, or a `ref` that isn't null or an existing entry id; trust ≠ computed |
| `entries_bi_links` (BEFORE INSERT) | links not an array of `{rel, target_id}`; an unknown rel; unsorted or duplicate links; a missing, later or self target; a rel not allowed for this author, channel, event and target; a lab `tool_result` without a `responds_to` to a `self` action |
| `entries_ai_fanout` (AFTER INSERT) | nothing; inserts one `links` row per element of `json_each(NEW.links)` |
| `entries_bu_redaction_only` (BEFORE UPDATE) | every UPDATE except: content and salt both go from non-null to null, every other column is `IS`-equal, the target isn't seq 1, and a `redacts` link to it exists from a `system_event` by user or system whose `data.event` IS `"redaction"` |

| `links_bu_forbid`, `links_bd_forbid` | everything |
| `meta_bi_guard` | an unknown or existing key; any insert once the record holds more than genesis; a value ≠ genesis `data` |
| `meta_bu_forbid`, `meta_bd_forbid` | everything |
